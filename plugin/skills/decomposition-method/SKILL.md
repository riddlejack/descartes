# Building the issue tree

The tree breaks the question asked into the sub-questions whose answers, together, answer it. Your reasoning about the question (its terms, the working answer and its rival, why you chose this cut) goes in frame.md; the tree holds only the questions.

1. **Cut by the logic that produces the answer.** Try two or three first cuts: the equation behind a number (revenue and cost; volume and price), the stages of a process, the competing causes, the conditions a choice depends on, or a standard framework when it fits this question (Ansoff's four routes for where growth can come from). Keep the cut under which a wrong answer would show most easily, and say why in frame.md.

2. **Each node is one short question.** One idea, plain words, readable alone. The root is the question as the user asked it; a question with several parts gets each part as a child. A node that needs "and", a list, a parenthesis, a rule, a bound, a source or a pointer to another node is either several questions, which become its children, or a note on how to answer it, which goes in settles_by.

3. **Children split their parent.** Each child is a part of its parent, not a method for answering it; together they answer the parent; no two overlap. A parent does not list or summarise its children. A node has no children or at least two.

4. **Go deeper where a node still has parts** that would be researched separately; stop when one finding would answer it. Branches differ in depth.

5. **The tree holds only sub-questions of the question asked.** No option, rival, check or work plan is a node. For a decision among named options, the top parts are what the choice turns on, asked of every option alike. For a question asking which options are best, the first part finds the candidates. Keep one open_lane node for primary reading nobody planned.

6. **Fill the fields, not the statement.** doubt, settles_by and flip_point are for leaves; a parent needs none. Mark the one to three nodes the answer turns on as crux. Leaves that rest on the same sources share one branch_id: a branch, not a leaf, is one worker's job.

7. **Revise by restructuring.** When a check or a critique finds a gap, an overlap or a node doing two jobs, add, split, move or merge nodes; never fix a tree by adding words to a node.
